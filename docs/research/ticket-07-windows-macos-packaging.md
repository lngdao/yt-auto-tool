# Ticket 07 — Windows and macOS packaging research

**Research date:** 2026-09-28  
**Scope:** Tauri v2 packaging for Windows x64 and macOS Apple Silicon, Python worker, yt-dlp, FFmpeg H.264/libass support, Tesseract OCR data, native dialogs, signing, and smoke checks. The selected first-version toolchain is recorded in `scripts/toolchain-lock.json`; packaging commands are in [packaging.md](../packaging.md).

## Recommendation

Keep the Tauri v2 app and package target-specific tools as resources beneath its app bundle. Build Windows x64 and macOS Apple Silicon in separate native CI jobs. Package Tesseract language data as read-only resources. Use PyInstaller one-folder for the Python worker because its executable depends on adjacent support files; launch it from Tauri Rust with absolute paths to the packaged tools. This avoids relying on the user's PATH, Python installation, or package manager, while leaving each tool independently diagnosable. Tauri preserves resource paths, and PyInstaller output is specific to the OS and CPU architecture used to build it. ([Tauri bundle resources](https://v2.tauri.app/reference/config/#bundleresources), [PyInstaller operating modes](https://pyinstaller.org/en/stable/operating-mode.html))

Suggested asset map:

| Component | Packaging direction |
| --- | --- |
| Python worker | Build a PyInstaller one-folder executable on each target runner and keep its adjacent support folder in the Tauri resource tree. ([Tauri bundle resources](https://v2.tauri.app/reference/config/#bundleresources), [PyInstaller](https://pyinstaller.org/en/stable/operating-mode.html)) |
| yt-dlp | Use upstream standalone release artifacts: `yt-dlp.exe` for Windows x64 and `yt-dlp_macos` for macOS (universal). Pin the release and verify the SHA-256 digest GitHub publishes for the release asset. The current packaged version is `2026.08.19`. ([yt-dlp release files and verification](https://github.com/yt-dlp/yt-dlp#release-files)) |
| FFmpeg + ffprobe | Build or provision a pinned target-specific pair. Require the `subtitles` filter (`libass`) and a known H.264 encoder in the shipped build; probe capabilities at startup and fail with an actionable message if they are absent. ([FFmpeg filters](https://ffmpeg.org/ffmpeg-filters.html#subtitles), [FFmpeg codecs](https://ffmpeg.org/ffmpeg-codecs.html)) |
| JavaScript runtime | Ship target-native Deno because yt-dlp currently enables it by default for YouTube JavaScript challenge extraction. The current package pins Deno `2.9.7`. ([yt-dlp EJS runtime](https://github.com/yt-dlp/yt-dlp/wiki/ejs), [Deno releases](https://github.com/denoland/deno/releases)) |

([Tesseract CLI](https://github.com/tesseract-ocr/tesseract/blob/main/doc/tesseract.1.asc), [tessdata_fast](https://github.com/tesseract-ocr/tessdata_fast)) |

## Tauri targets and resources

The app uses the Tauri `bundle.resources` tree instead of `bundle.externalBin` for the PyInstaller worker. Its one-folder build needs the adjacent `_internal` directory to stay next to the executable. Rust resolves the worker and tools from the app resource directory, then passes the database and tool paths as structured arguments and environment variables. ([Tauri bundle resources](https://v2.tauri.app/reference/config/#bundleresources), [PyInstaller operating modes](https://pyinstaller.org/en/stable/operating-mode.html))

Bundle immutable support data such as `tessdata/eng.traineddata` and `tessdata/vie.traineddata` in `bundle.resources`; Tauri preserves resource paths or allows explicit destination mapping. Use the app’s resource directory for reads and a user data/output directory for writes. ([Tauri bundle resources](https://v2.tauri.app/reference/config/#bundleresources), [Tauri resource path scopes](https://v2.tauri.app/plugin/file-system/#scopes))

Use Tauri’s native dialogs for folder and file selection. The dialog API is supported on both target OSes and returns ordinary filesystem paths there. If frontend code also uses the filesystem plugin, configure only the required scopes; plugin access is path-scoped. ([Tauri Dialog plugin](https://v2.tauri.app/plugin/dialog/), [Tauri File System scopes](https://v2.tauri.app/plugin/file-system/#scopes))

Tauri uses the system WebView: WKWebView on macOS and WebView2 on Windows. The Windows installer normally downloads/runs the WebView2 bootstrapper if the runtime is missing; offline installation can embed the offline installer, adding about 127 MB. Keep this distinct from the app’s own media/OCR dependencies in installer checks. ([Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/), [Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/#webview2-installation-options))

## Worker and build pipeline

PyInstaller output is specific to the active OS, Python version, and bitness, so build the worker separately on Windows x64 and macOS arm64. Keep the one-folder result intact because the executable uses its adjacent support directory. ([PyInstaller operating modes](https://pyinstaller.org/en/stable/operating-mode.html))

Use native CI runners: Windows x64 for `x86_64-pc-windows-msvc`, and an Apple Silicon macOS runner for `aarch64-apple-darwin`. Tauri’s GitHub Actions guide demonstrates this matrix and calls `macos-latest` the Apple Silicon runner. Tauri says Windows cross-compilation is possible with caveats; MSI creation requires Windows, and NSIS cross-compilation is a last resort. Native runners also keep PyInstaller output architecture-aligned. ([Tauri GitHub pipeline](https://v2.tauri.app/distribute/pipelines/github/), [Tauri Windows installer build notes](https://v2.tauri.app/distribute/windows-installer/#build-windows-apps-on-linux-and-macos), [PyInstaller operating modes](https://pyinstaller.org/en/stable/operating-mode.html))

Each CI job should pin tool versions and emit a manifest containing the target triple, tool versions, hashes, FFmpeg `-buildconf`, and the expected OCR model names. Stage those outputs into Tauri’s sidecar/resource paths before `tauri build`. This manifest is a packaging recommendation: reproducible, target-pinned artifacts are necessary to validate the tool capability checks described below.

## yt-dlp provisioning

Upstream lists `yt-dlp.exe` as the recommended Windows standalone x64 build and `yt-dlp_macos` as the recommended universal macOS executable. Upstream publishes SHA2 checksum files and detached GPG signatures, with its public key and verification commands in the same README. The README also notes that PyInstaller-bundled release executables include GPLv3+ code and ship third-party license information; include those notices and review redistribution terms before publishing the app. ([yt-dlp release files and licensing](https://github.com/yt-dlp/yt-dlp#release-files))

Use release artifacts from the official `yt-dlp/yt-dlp` repository, pin the release rather than pulling a floating `latest` URL during normal builds, and verify GitHub's published SHA-256 asset digest in CI. The downloader's release executable is a separate child process; this avoids coupling its standalone build to the frozen Python worker. Current yt-dlp also uses a JavaScript runtime for full YouTube extraction; the package places Deno on `PATH`. ([yt-dlp release files](https://github.com/yt-dlp/yt-dlp#release-files), [yt-dlp EJS runtime](https://github.com/yt-dlp/yt-dlp/wiki/ejs))

## FFmpeg capability and licensing choice

FFmpeg’s `subtitles` filter renders subtitle files through libass and is only available when FFmpeg was configured with `--enable-libass`. The FFmpeg CLI provides `-filters`, `-encoders`, `-buildconf`, and `-h filter=...`/`-h encoder=...` for capability checks. Check `subtitles` and the chosen H.264 encoder at app startup; version output alone does not prove required components exist. ([FFmpeg subtitles filter](https://ffmpeg.org/ffmpeg-filters.html#subtitles), [FFmpeg CLI](https://ffmpeg.org/ffmpeg.html))

FFmpeg’s official download page says it distributes source code only and points users to external binary providers. The app therefore needs either a controlled per-target build or a selected binary provider whose build configuration and redistribution terms are pinned and audited. A provider’s build must be checked for the required filter/encoder rather than inferred from its “full” or “static” label. ([FFmpeg download page](https://ffmpeg.org/download.html))

For the platform-native H.264 route, FFmpeg’s Media Foundation wrapper exposes `h264_mf` on Windows and supports software or hardware encoding; hardware mode requires D3D11. FFmpeg’s Apple VideoToolbox source contains an H.264 encoder implementation. Validate the exact encoder in the packaged binary and on the actual target machine, since available options/runtime support can vary. ([FFmpeg Media Foundation codecs](https://ffmpeg.org/ffmpeg-codecs.html#MediaFoundation), [FFmpeg VideoToolbox encoder source](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/videotoolboxenc.c))

If the app chooses `libx264` for a consistent software-encoding path, FFmpeg upstream says it must be enabled at build time and its GPL licensing applies to FFmpeg when GPL components such as libx264 are used. This makes the encoder choice a release/licensing decision, not just a speed toggle. If avoiding the GPL build route, use the target-native H.264 encoders and maintain per-platform settings and tests. ([FFmpeg libx264 docs](https://ffmpeg.org/ffmpeg-codecs.html#libx264), [FFmpeg license notes](https://ffmpeg.org/legal.html))

For the app’s composition pipeline, the CLI supports infinite input looping with `-stream_loop -1`, explicit stream selection with `-map`, and ending the output when the shortest output stream finishes with `-shortest`. This fits “loop background, use source audio duration, burn captions, encode 1280×720,” while avoiding accidental use of the source video stream. FFmpeg also exposes machine-readable `-progress` output. ([FFmpeg CLI options and stream mapping](https://ffmpeg.org/ffmpeg.html), [FFmpeg progress output](https://ffmpeg.org/ffmpeg.html#toc-Generic-options))

## Tesseract engine and language data

Tesseract treats the engine and traineddata as separate pieces. Its CLI supports `--tessdata-dir PATH` and `--list-langs`, and upstream documents installing one or more language models separately. `tessdata_fast` is the faster LSTM model repository and includes Vietnamese; the Tesseract CLI documents that `tessdata_fast` models require the LSTM engine (`--oem 1`). Bundle only the OCR languages the app actually supports, such as `eng` and `vie`, and pass their directory explicitly. ([Tesseract install guide](https://github.com/tesseract-ocr/tessdoc/blob/main/Installation.md), [Tesseract CLI](https://github.com/tesseract-ocr/tesseract/blob/main/doc/tesseract.1.asc), [tessdata_fast](https://github.com/tesseract-ocr/tessdata_fast))

The Tesseract project links Windows users to UB Mannheim installers rather than publishing an upstream Windows installer. On macOS the upstream installation guide points users to Homebrew/MacPorts. Homebrew currently has Apple Silicon bottles, but its formula has a significant native dependency tree and ships only `eng`/`osd` by default. For a self-contained app, produce and validate app-owned Tesseract artifacts per target instead of assuming a Homebrew installation; if building that is deferred, make first-run provisioning explicit and fail clearly until the engine and model data are available. ([Tesseract installation guide](https://github.com/tesseract-ocr/tessdoc/blob/main/Installation.md), [Homebrew Tesseract formula](https://formulae.brew.sh/formula/tesseract))

Tesseract and `tessdata_fast` are Apache-2.0, but Tesseract notes that dependencies can use different licenses. Include notices for the exact engine build, native libraries, and model files that ship. ([Tesseract license/dependency note](https://github.com/tesseract-ocr/tesseract#license), [tessdata_fast license](https://github.com/tesseract-ocr/tessdata_fast/blob/main/LICENSE))

## Local builds vs external distribution

- **Local development:** The distribution docs scope Apple signing to App Store/browser distribution, and the GitHub pipeline describes ad-hoc signing for unsigned Apple Silicon release artifacts; therefore a signing identity/notarization step is not a local `tauri dev` prerequisite (inference from those distribution requirements). For Apple Silicon apps downloaded from a browser, Tauri documents that ad-hoc signing can help avoid the “damaged” message, but users may still need to whitelist the app in Privacy & Security. ([Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/), [Tauri GitHub pipeline](https://v2.tauri.app/distribute/pipelines/github/))
- **macOS external distribution:** Direct-download apps need a Developer ID Application signature to avoid the browser-download warning; notarization is required with that certificate. A free Apple developer account cannot notarize. Treat the Developer ID certificate and notarization credentials as release secrets, not development prerequisites. ([Tauri macOS signing and notarization](https://v2.tauri.app/distribute/sign/macos/))
- **Windows external distribution:** Code signing is required for Microsoft Store and prevents the “not trusted” SmartScreen warning, but Tauri notes an unsigned app can still execute if the user accepts the warning. SmartScreen reputation can still take time to build even for a signed app. ([Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/))

## Smoke-test workflow for Ticket 07

Run the following on clean Windows x64 and macOS Apple Silicon machines/VMs using the actual packaged installer, with system Python and media tools absent where possible:

1. Launch the installed app; run a worker health check that reports the OS/architecture and exact worker, yt-dlp, FFmpeg/ffprobe, Tesseract, and model versions. Tauri’s sidecar rules and PyInstaller’s per-platform build behavior make this an important check of the generated target files. ([Tauri sidecars](https://v2.tauri.app/develop/sidecar/), [PyInstaller](https://pyinstaller.org/en/stable/operating-mode.html))
2. Confirm `yt-dlp --version`; `ffmpeg -filters` contains `subtitles`; `ffmpeg -encoders` or `-h encoder=...` shows the selected H.264 encoder; and `tesseract --list-langs --tessdata-dir <bundled-data-dir>` shows each configured language. ([yt-dlp README](https://github.com/yt-dlp/yt-dlp), [FFmpeg CLI](https://ffmpeg.org/ffmpeg.html), [Tesseract CLI](https://github.com/tesseract-ocr/tesseract/blob/main/doc/tesseract.1.asc))
3. Use the native dialog to choose a local background clip and output folder. Render a checked-in short audio/video fixture plus an SRT/ASS fixture, with no YouTube request or credentials. Render at 1280×720, loop the background, select only the source audio and background video streams explicitly, and burn the caption through the verified `subtitles` filter. ([Tauri Dialog plugin](https://v2.tauri.app/plugin/dialog/), [FFmpeg stream mapping and loop options](https://ffmpeg.org/ffmpeg.html), [FFmpeg subtitles filter](https://ffmpeg.org/ffmpeg-filters.html#subtitles))
4. Check a successful exit, progress reaches 100%, the generated file contains 1280×720 H.264 video and the expected audio stream, and a sampled frame visibly contains the caption. Repeat with deliberately missing/corrupt tool or model input and verify the app names the missing capability rather than presenting a generic render failure. FFmpeg supports machine-readable progress events and `ffprobe` is included in its official tooling. ([FFmpeg progress](https://ffmpeg.org/ffmpeg.html#toc-Generic-options), [FFprobe documentation](https://ffmpeg.org/ffprobe.html))
5. On Windows, test the normal WebView2-bootstrapper path and, if offline installation is a requirement, the offline installer mode. On macOS, test the local unsigned/ad-hoc build separately from a signed/notarized distribution artifact. ([Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/#webview2-installation-options), [Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/))

## Implemented first-version choices

The app pins FFmpeg `9.0.2`, yt-dlp `2026.08.19`, Deno `2.9.7`, and Tesseract `5.5.3` in `scripts/toolchain-lock.json`. Windows packaging stages the static FFmpeg Full build and Tesseract installed by pinned Chocolatey packages. macOS packaging installs FFmpeg and Tesseract through Homebrew, then uses `dylibbundler` to copy Tesseract's non-system dylibs into the resource tree. Both targets download yt-dlp and Deno from their official GitHub releases and verify the SHA-256 asset digests. English and Vietnamese fast OCR models come from a pinned `tessdata_fast` commit.

FFmpeg uses `libx264`, so the selected build is GPL-enabled. `docs/packaging.md` records the build commands, bundled license files, release restrictions, and smoke-test behavior. `scripts/smoke_package.py` validates worker startup, required FFmpeg encoders/filter, a local audio/background/SRT render, and a local Tesseract OCR fixture. `.github/workflows/package-smoke.yml` runs the checks on both native target runners and builds the Tauri package.
